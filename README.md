## Pages

- `/`: app cards (`docs/index.md`).
- `/apps/<slug>`: features, screenshots and What's New for each app (`docs/apps/<slug>.md`). Each page sets its own og/twitter share card (1200×630), always `/img/apps/<slug>/og.jpg`, generated by [`scripts/og-card/`](scripts/og-card/README.md). Binary images are **not** stored on `master`; they live on the orphan [`assets`](https://github.com/PrimaAestate/primaaestate.github.io/tree/assets) branch and are synced into `docs/public/` at build time.
- `/updates`: release notes for all apps, newest first.
- `/Feedback`: feedback form. Submissions become public issues in [PrimaAestate/feedback](https://github.com/PrimaAestate/feedback) through the Cloudflare Worker in [`worker/`](worker/README.md). The app list is `docs/data/apps.json` (keep in sync with `worker/src/apps.json`).
- `/PrivacyPolicy`.

## Development

Built with [VitePress](https://vitepress.dev).

```sh
npm i
./scripts/sync-assets.sh   # fetch orphan `assets` → docs/public/img + og-default.jpg
npm run docs:dev           # local preview
npm run docs:build         # output: docs/.vitepress/dist
```

`docs/public/img/` and `docs/public/og-default.jpg` are gitignored on `master`. After a fresh clone, run `./scripts/sync-assets.sh` (or keep local copies from a previous checkout) so `docs:dev` can serve page shots and OG cards. `docs/public/CNAME` and `logo.svg` stay on `master`.

OG source screens under `scripts/og-card/screens/` are also gitignored (regenerable from each app's store screenshot script).

## Site images (`assets` branch)

Page shots, app icons and OG JPEGs live on an **orphan** branch named `assets` (tree: `img/…`, `og-default.jpg`). Each update force-pushes a **single new root commit** so image history does not accumulate in git.

```sh
# After regenerating files under docs/public/img and/or og-default.jpg:
./scripts/publish-assets.sh   # orphan commit → force-push origin/assets
```

CI (`main.yml` and `app-release.yml`) runs `git archive origin/assets` into `docs/public/` before `vitepress build`. URLs stay `/img/apps/...`; GitHub Pages still publishes from `gh-pages` only.

## Deploy

Pushing to `master` runs `.github/workflows/main.yml`, which syncs `assets`, builds the site, and publishes `docs/.vitepress/dist` to the `gh-pages` branch with `force_orphan: true` (deploy history is not kept). The custom domain is set in `docs/public/CNAME` (`www.primaaestate.cloud`).

## App changelogs

App pages and `/updates` read release history from `docs/data/changelogs/<slug>.json`.

**Automatic (on release):** each app repo has `.github/workflows/notify-site.yml`. Pushing a `v*` tag reads the
version and en-US notes (`fastlane/i18n-release-notes.json`, falling back to `CHANGELOG.md`) and sends a
`repository_dispatch` (`app-release`) to this repo with `{slug, version, date, notes}`.
`.github/workflows/app-release.yml` here merges it (`scripts/merge-changelog.py`, upsert by version, Aestate wording
filter), commits to `master`, then builds and deploys (a push made with `GITHUB_TOKEN` does not trigger `main.yml`).
App repos need secret `SITE_DISPATCH_TOKEN`: a fine-grained PAT, repository access *PrimaAestate/primaaestate.github.io* only, permission *Contents: Read and write*.

Test locally:

```sh
printf '%s' '{"slug":"nomedia","version":"9.9.9","date":"2026-01-01","notes":"Bug Fixes\n\n- Example"}' > /tmp/p.json
python3 scripts/merge-changelog.py /tmp/p.json && git diff docs/data/changelogs
```

**Manual fallback / full rebuild from App Store Connect (read-only):**

```sh
pip install pyjwt cryptography requests
ASC_KEY_ID=... ASC_ISSUER_ID=... ASC_PRIVATE_KEY="$(cat AuthKey_XXXX.p8)" python3 scripts/fetch-changelogs.py          # all apps
python3 scripts/fetch-changelogs.py nomedia   # one app
```

## Server-side updates (reviewed separately from app releases)

The existing app-page changelog and `/updates` also render
`docs/data/server-updates/shared.json`. Keep service notes separate from
`docs/data/changelogs/`: App Store imports and `app-release` dispatches own the
app files and must not overwrite service history. There is no server-release
dispatch or automatic backend-tag integration. Do not invoke the app-release
workflow for a service deployment; it writes directly to `master`.

Each shared row has an actual rollout `date` (`YYYY-MM-DD`), plain-text `notes` that use the same section headings as app What's New (`Features`, `Bug Fixes`, `Improvements`, `Performance Improvements`),
and an `apps` list of slugs that should show the note (for example
`hello-hero` and `web-copilot`). An optional `version` may identify a
**verified server tag for that rollout**; it is never an App Store version.
Until a matching server tag exists, omit it: the UI says **Server update**
and shows the date. A stale latest tag or a package.json version is not
evidence of a deployment version. Optional `extras.<slug>` text is appended
for that app only, inserted before the last bullet of `notes` so a shared
closing line stays last. `/updates` shows one row per shared entry and lists
every affected app; each app page shows only rows that include that slug,
with extras already merged.

### Customer-visible service release checklist

- After a verified service rollout, explicitly decide whether model availability,
  token deductions, voice pricing, or other user-visible behavior needs a site
  update. Document “no customer-visible change” when no entry is needed.
- Prepare a website PR that updates the shared server-update file (and extras
  when only some apps are affected). Explain any increased charge, differences
  between model discounts, client-version limitations, and scheduled price
  changes (with an explicit time zone). Do not call a mixed-model change “half
  price” or imply an App Store release occurred.
- Check both the app page and `/updates`, while preserving every app-release
  row. The current website has one language (`en-US`); app language support is
  not a website locale list. If website locales are added, cover each of them.
- Run `npm test`, `./scripts/sync-assets.sh`, and `npm run docs:build`; review
  the rendered pages. Never publish endpoints, infrastructure identifiers,
  private deployment evidence, sales, credentials, or customer data.
- Link the site PR from the service release checklist/PR. Wait for owner approval
  before merging/publishing either PR. Tagging, creating a release, dispatching
  a workflow, or pushing `master` needs its own explicit approval; adding notes
  does not authorize any of these actions.
